# The Toolshed — Blog Publishing System

An Astro-native, static-first blog built to be published to by an automated
n8n content pipeline. No CMS, no database — every article is a Markdown
file committed to this repo, built by Astro, and deployed by Netlify.

> This repository was empty when this system was built (no prior Astro
> site existed), so the site itself — homepage, blog, design, SEO — was
> created from scratch alongside the publishing pipeline described below.

## How it fits together

```
n8n (generate → QC → your approval)
   │
   │ POST /api/blog/publish  (Netlify Function, requires API key)
   ▼
GitHub Contents API → commits src/content/blog/<slug>.md
   │
   │ push to `main` triggers Netlify's GitHub integration
   ▼
Netlify build → astro build → static pages + /api/content-index.json
   │
   ▼
Live at https://<your-site>/blog/<slug>
```

There is no intermediate database or queue. The Markdown file *is* the
article. This means the publish endpoint's job is narrow and safe: validate
the request, then make one commit.

## Where articles live

- **Content**: `src/content/blog/<slug>.md` — one Markdown file per
  article, frontmatter + body. The filename is always the article's slug.
- **Schema**: `src/content.config.ts` defines and validates every
  frontmatter field (title, description, dates, category, tags, keywords,
  author, images, SEO overrides, source attribution, internal links,
  `draft`). Astro rejects the build if a file doesn't match this shape.
- **Routes**:
  - `/blog` — index of published (non-draft) articles, newest first.
  - `/blog/[slug]` — a single article: SEO meta, canonical URL, JSON-LD
    `Article` structured data, featured image, source attribution,
    resolved internal links, and a "Related Articles" section computed
    from category/tag/keyword overlap (never fabricated).
  - `/blog/category/[category]` — one static page per category.
  - `/rss.xml` — RSS feed of published articles.
  - `/sitemap-index.xml` — generated by `@astrojs/sitemap` automatically.

Draft articles (`draft: true`) are never built into a page and never
appear in the index, RSS feed, or sitemap.

## The content index (for internal linking)

`GET /api/content-index.json` is a static file, regenerated on every
build directly from the content collection. It lists every published
article:

```json
{
  "generatedAt": "2026-08-16T23:14:41.221Z",
  "count": 1,
  "articles": [
    {
      "title": "Welcome to The Toolshed Blog",
      "slug": "welcome-to-the-toolshed-blog",
      "url": "https://your-site.netlify.app/blog/welcome-to-the-toolshed-blog",
      "category": "Announcements",
      "tags": ["announcements", "automation"],
      "keywords": ["toolshed blog", "astro blog", "ai content pipeline"],
      "summary": "How this blog works: ...",
      "publishedDate": "2026-08-16T00:00:00.000Z",
      "updatedDate": null
    }
  ]
}
```

**n8n should fetch this before generating `internalLinks`** and only ever
reference `slug` values that appear here. On the article page,
`internalLinks` entries that don't resolve to a real, published slug are
silently dropped — the AI pipeline cannot cause the site to link to a URL
that doesn't exist.

The index updates automatically: publishing an article triggers a Netlify
build, and the build regenerates this file from whatever's currently in
`src/content/blog`. It's eventually consistent — allow the ~1–2 minutes a
Netlify build takes before an article shows up here or on `/blog`.

## Publishing endpoint

```
POST /api/blog/publish
```

This is the only dynamic route in the project (`export const prerender =
false`); everything else is static HTML/JSON. It runs as a Netlify
Function via the `@astrojs/netlify` adapter.

### Authentication

Send the shared secret either as:

```
x-api-key: <BLOG_PUBLISH_API_KEY>
```

or

```
Authorization: Bearer <BLOG_PUBLISH_API_KEY>
```

Requests without a matching key get `401` before anything else runs. The
key is read at runtime from the `BLOG_PUBLISH_API_KEY` environment
variable via Astro's `astro:env/server` module — it is never bundled into
client code or the static build output.

### Request body

```json
{
  "title": "5 Ways to Automate Your Home Workshop",
  "description": "A practical guide to workshop automation for hobbyists.",
  "slug": "5-ways-to-automate-your-home-workshop",
  "publishedDate": "2026-08-16",
  "category": "DIY & Tools",
  "tags": ["automation", "workshop"],
  "keywords": ["home workshop automation", "diy tools"],
  "seoTitle": "5 Ways to Automate Your Home Workshop",
  "metaDescription": "Practical workshop automation tips for hobbyists and makers.",
  "content": "## Intro\n\nMarkdown body of the article goes here...",
  "featuredImage": "https://images.example.com/workshop.jpg",
  "featuredImageAlt": "A tidy automated workshop",
  "sourceArticle": "Original research title",
  "sourceUrl": "https://example.com/source",
  "sources": [
    "https://example.com/source-2",
    { "title": "A Named Study", "url": "https://example.com/study" }
  ],
  "internalLinks": ["welcome-to-the-toolshed-blog"]
}
```

Only `title`, `description`, `slug`, `category`, and `content` are
required; everything else is optional. `publishedDate` defaults to "now"
if omitted. `draft: true` can be sent to commit a post without it
appearing on the live site or in the content index yet.

### What the endpoint does, in order

1. **Authenticate** the API key (constant-time comparison).
2. **Parse and validate** the JSON body against a strict schema (Zod) —
   malformed JSON or missing/invalid fields return `400` with the specific
   validation issues, no server internals exposed.
3. **Normalize and re-validate the slug** (lowercased, non `[a-z0-9-]`
   characters collapsed to hyphens, leading/trailing hyphens trimmed).
   Because the slug becomes the filename, this also closes off path
   traversal — a slug can never contain `/`, `..`, or similar.
4. **Check for a duplicate** via the GitHub Contents API
   (`GET /repos/:owner/:repo/contents/src/content/blog/<slug>.md`). If the
   file already exists, respond `409` and do not touch the repo.
5. **Sanitize content**: the Markdown body is run through `sanitize-html`
   with a conservative allowlist (strips `<script>`, event handlers,
   `javascript:` URLs, iframes, forms, etc. — plain Markdown syntax is
   untouched since it isn't HTML). Plain-text fields (title, description,
   category, alt text, etc.) have all HTML stripped.
6. **Build frontmatter** safely via `js-yaml`'s `dump()` (handles quoting/
   escaping automatically — no manual string concatenation into YAML).
7. **Commit** the new file via the GitHub Contents API
   (`PUT .../contents/src/content/blog/<slug>.md`), which is a real commit
   to the branch Netlify deploys from.
8. **Respond** with the result.

### Example response (success)

```json
{
  "success": true,
  "slug": "5-ways-to-automate-your-home-workshop",
  "url": "https://your-site.netlify.app/blog/5-ways-to-automate-your-home-workshop",
  "status": "published",
  "title": "5 Ways to Automate Your Home Workshop",
  "contentIndexUpdated": true,
  "commitUrl": "https://github.com/japage1928/thetoolshed/blob/main/src/content/blog/5-ways-to-automate-your-home-workshop.md",
  "note": "Committed to GitHub; Netlify will build and deploy automatically. The live page and /api/content-index.json typically update within a couple of minutes."
}
```

`contentIndexUpdated: true` means the commit that will regenerate the
index has been made — not that the index is live *this second*. Netlify's
build still needs to run (usually well under two minutes).

### Example response (duplicate slug)

```json
{
  "success": false,
  "error": "duplicate_slug",
  "message": "An article with slug \"5-ways-to-automate-your-home-workshop\" already exists.",
  "slug": "5-ways-to-automate-your-home-workshop",
  "url": "https://your-site.netlify.app/blog/5-ways-to-automate-your-home-workshop"
}
```
HTTP status `409`.

### Other error responses

| Status | `error`               | Cause                                      |
| ------ | --------------------- | ------------------------------------------- |
| 401    | `unauthorized`        | Missing/incorrect API key                   |
| 400    | `invalid_json`        | Body isn't valid JSON                       |
| 400    | `validation_failed`   | Missing/invalid fields (see `issues`)       |
| 400    | `invalid_slug`        | Slug has no usable characters after normalizing |
| 409    | `duplicate_slug`      | An article with that slug already exists    |
| 500    | `server_misconfigured`| `GITHUB_TOKEN` not set in the environment   |
| 502    | `github_error`        | GitHub API call failed (bad token, rate limit, etc.) |
| 500    | `internal_error`      | Unexpected server error                     |

No response ever includes environment variable values, stack traces, or
the API key/token.

## Required environment variables

Set these in **Netlify → Site configuration → Environment variables**
(never commit real values — see `.env.example`):

| Variable                | Required | Purpose |
| ------------------------ | -------- | ------- |
| `PUBLIC_SITE_URL`         | Recommended | Canonical base URL used for canonical links, sitemap, RSS, OG/Twitter tags, and the `url` field in API responses. |
| `BLOG_PUBLISH_API_KEY`    | Yes      | Shared secret n8n sends in `x-api-key` / `Authorization: Bearer`. Generate a long random string. |
| `GITHUB_TOKEN`            | Yes      | Fine-grained GitHub PAT scoped to this repo only, with **Contents: Read and write** permission. Used to commit new articles. |
| `GITHUB_OWNER`            | No (defaults to `japage1928`) | Repo owner the publish endpoint commits to. |
| `GITHUB_REPO`             | No (defaults to `thetoolshed`) | Repo name the publish endpoint commits to. |
| `GITHUB_BRANCH`           | No (defaults to `main`) | Branch to commit to — must be the branch Netlify auto-deploys. |

All of these are read server-side only via `astro:env/server`, so they're
never included in the static build output or exposed to the browser.

## How n8n should call it

```
POST https://your-site.netlify.app/api/blog/publish
Content-Type: application/json
x-api-key: <BLOG_PUBLISH_API_KEY>

{ ... payload as documented above ... }
```

On `200`, the article is committed and will go live once Netlify's build
finishes. On `409`, treat it as "already published" — nothing further to
do. On `4xx`/`5xx`, log the response body (it contains a safe, specific
`error` code and `message`) and alert for human review rather than
retrying blindly.

## Testing the endpoint

Locally:

```bash
npm install
cp .env.example .env   # fill in a test BLOG_PUBLISH_API_KEY and a real GITHUB_TOKEN
npm run dev
```

```bash
curl -X POST http://localhost:4321/api/blog/publish \
  -H "Content-Type: application/json" \
  -H "x-api-key: $BLOG_PUBLISH_API_KEY" \
  -d '{
    "title": "Test Article",
    "description": "A test article for verifying the publish pipeline.",
    "slug": "test-article",
    "category": "Announcements",
    "content": "## Hello\n\nThis is a test."
  }'
```

Expect `200` with `"success": true` and a `commitUrl`. Re-running the same
request should now return `409 duplicate_slug`. Check GitHub for the new
commit adding `src/content/blog/test-article.md`, then check Netlify's
deploy log to confirm a build kicked off from that commit.

Against production, do the same against
`https://your-site.netlify.app/api/blog/publish` — this is a real commit,
so only use real payloads (or delete the test file/commit afterward).

## Deployment

- **Netlify** builds with `npm run build` (`astro build`, via
  `netlify.toml`) and deploys the `@astrojs/netlify` adapter's output.
  Connect this GitHub repo to a Netlify site in the usual way (Netlify →
  Add new site → Import from GitHub) and set the environment variables
  above on that site.
- Every push to the deploy branch (`GITHUB_BRANCH`, typically `main`) —
  whether from a human or from `/api/blog/publish` — triggers a normal
  Netlify build and deploy. There is no separate deploy step the publish
  endpoint has to trigger; committing *is* the trigger.
- The blog is fully static except for `/api/blog/publish` itself.
  `/api/content-index.json`, `/blog`, `/blog/[slug]`, `/rss.xml`, and the
  sitemap are all pre-rendered at build time — fast, and with effectively
  no client-side JavaScript.

## End-to-end test: n8n → Astro → Netlify → live URL

1. From n8n (or `curl`), `POST /api/blog/publish` with a real payload and
   the correct `x-api-key`.
2. Confirm the response is `200` with `"success": true` and note the
   `slug` and `commitUrl`.
3. Open `commitUrl` (or the repo's commit history) — confirm a new commit
   added `src/content/blog/<slug>.md` to the deploy branch.
4. In the Netlify dashboard, confirm a new deploy started from that
   commit and finishes successfully.
5. Visit `https://your-site.netlify.app/blog/<slug>` — the article should
   be live with correct title, dates, category, and (if provided) featured
   image.
6. Visit `https://your-site.netlify.app/api/content-index.json` — the new
   article should now be listed, ready for the next n8n run to reference
   in `internalLinks`.
7. Re-POST the same payload — confirm you now get `409 duplicate_slug`
   instead of a second commit.
